# dsh-ob-agent 使用文档

统一管理 DSH 里**全部 agent 类工具**的插件：一个总开关、一张条目表、每会话勾选、
以及让模型自己创建 Agent 的能力。

- 面向模型的说明：`model-guide.md`（同一目录）
- 面向本插件的维护者：`../README.md`

## DSH 版本兼容

### 0.1.7 → 0.2.0-rc.2 的结论：主机侧 API 无破坏性变更

逐文件比对 `0.1.7-rc.2` 与 `0.2.0-rc.2` 的 `lib/`（含 `.d.ts`）后确认：本插件消费的
`dsh-tools`（`register` / `restrict` / `guard` / `get` / `schemas`）、`dsh-settings`
（volatile live Config + `configForms`）、`dsh-system-prompt`（`section` /
`getSectionOrder('TOOL_SUBAGENT')`）、`dsh-agent-preset(-registry)` 的**实现逐字节未变**。
客户端侧同样对齐：`conversation.input.dock` 与 `settings.section` 两个槽位仍在，
`host-ui.tsx` 里具名导入的 7 个图标与 6 个结构组件在 `dsh-client-ui-primitives@0.2.0-rc.2`
里全部存在，`styles.ts` 引用的 23 个设计令牌也全部仍在。

本次升级真正影响本插件的有三点，都已处理：

1. **`@deepseek-ai/dsh-workflow-worker-thread` 已下线**（最后发布 `0.1.5-rc.3`）。
   `workflowEngine` 服务现由 `@deepseek-ai/dsh-workflow` 提供，`dsh-tool-workflow` 也只
   peer 后者。仓库里对该包的 `declare module`、`peerDependencies` 条目与告警文案已清理；
   profile 里那条指向已删除路径的悬空 junction 可以删掉，不影响功能。
2. **属性表 ≠ JSON Schema**（见下节）：模型自助管理工具的 `parameters` 之前写成了
   `defineTool` 的作者侧 DSL，已改为模型可见的 JSON Schema。
3. 开发依赖 `@deepseek-ai/dsh-client-ui-primitives` 已钉到 `0.2.0-rc.2`，与实际宿主一致。

### 升级 DSH 后怎么复核

仓库里有一组**跑在真实 DSH 运行时上**的兼容性测试（`tests/dsh-compat.spec.ts`）：它用绝对
路径动态导入 `~/.dsh/profiles/node_modules` 里的 `cordis` / `dsh-tools` / `dsh-system-prompt`
等包，把本插件的**使用面假设**拿到上游实现上验证一遍（`restrict` 只接受继承面名字、
`schemas(agent)` 的作用域语义、裸定义能被 `register` 接受且参数模式是 object 根 JSON Schema、
四个工具包都还具名导出 `apply` / `name` 等）。找不到 DSH 时整组跳过，不影响普通 CI。

```powershell
npm test          # 兼容性测试会在有 DSH 的机器上自动跑起来
# 装在别处时用环境变量指路：
$env:DSH_PROFILE_NODE_MODULES = 'D:\dsh\profiles\node_modules'; npm test
```

升级 DSH 后请顺手做三件事：① 把 `devDependencies` 里的
`@deepseek-ai/dsh-client-ui-primitives` 改成与宿主相同的版本；② `npm test` 至少让
`tests/dsh-compat.spec.ts` 全绿；③ 若上游改了图标名或组件名，`npm run typecheck` 会先失败。

### 0.1.7 的两处破坏性变更（历史记录，本插件已适配）

1. **设置接口**：浏览器设置接口从 `settingsScope` 切换到 `configForms`，并要求 Host 插件通过
   live Config 暴露可编辑字段（字段要标 `.volatile()`，否则写入会被 Host 拒绝）。本插件已将
   设置迁至自身 `dsh-ob-agent` 配置项，浏览器与 Host 共用同一份 profile 配置。
2. **UI 图标命名**：产品图标从 `Icon<名>Outline<尺寸>`（例如 `IconPlusOutline16`）改为
   `Icon<名>OutlineRegular / Medium`（1px / 1.3px 描边），尺寸改由 `size` 属性表达。
   旧名字在 `0.1.7-rc.2` 与 `0.2.0-rc.2` 上**都不存在**，而客户端 bundle 把 UI 组件库当
   外部依赖在运行期加载 —— 缺失的导入就是 `undefined`，React 一渲染就抛错，槽位条目随后被
   摘除。**症状是聊天框的「子代理」条不出现、设置页「子代理」整片空白，控制台之外没有任何
   线索。** 适配集中在 `src/client/host-ui.tsx`：新名优先、旧名兜底（旧名那一层只对更老的
   宿主有意义，在受支持的 DSH 上是恒为 `undefined` 的具名导入），同一份产物两边都能渲染。

改这一层时有两条硬约束，都是踩过的坑：

- **只用具名导入**。宿主交给插件的模块对象不保证可以被属性枚举：`import * as ns` 走过打包器
  的名字空间副本，副本可能是**空的**，于是按名字查表会把完全正常的宿主误判成「缺件」。
  具名导入走模块系统自己的解析路径，没有这个风险。
- **自检只告警、绝不因此放弃注册**。缺一个图标的代价是那一处空着，而「因为自检就不注册」
  会让整个界面消失 —— 重启后连设置页的「子代理」导航项都没有，就是这个失败模式。

从旧版本升级时，原 `ob-agent` 命名空间可能留在 `~/.dsh/settings.yaml.imported`。把该段迁入 `~/.dsh/profiles/web/cordis.patch.yml` 中 `id: dsh-ob-agent` 的 `config`，保留全部字段，尤其是 `entries` 与 `sessions`；迁移后重启 DSH 并硬刷新页面。

### 工具参数为什么必须编译成 JSON Schema

模型可见的工具模式是 `ToolSchema.parameters`，上游注释写得明确：**JSON Schema object for
the arguments**（根是 `{ type: 'object', properties, required }`）。而
`{ 字段名: { type, required, description } }` 这种写法只是 `defineTool` 的**作者侧 DSL**，
要经上游 `parameterSchemaSpecToJsonSchema` 编译后才变成模型看到的样子。

本插件刻意不依赖 `@deepseek-ai/dsh-tools`（它只发布在 DSH 自己的解析链上），`agent_create` /
`agent_update` / `agent_list` 三个工具是**裸注册**的，所以这一步得自己做（`authoring.ts` 的
`parameterSchemaOf`）。漏做**不会报错**，只会静默降级：Anthropic 系 provider 因为
`input_schema` 不是 object 而拒绝整个请求，OpenAI 系 provider 则把每个字段名当成未知关键字，
参数说明形同虚设 —— 模型只能靠描述猜参数名。`tests/dsh-compat.spec.ts` 会在真实登记表上
断言这三个工具的 `parameters.type === 'object'`，防止再次退化。

## 1. 它解决什么问题

DSH 默认把委派与编排工具**直接暴露**给模型：`subagent`、`subagent_fork`、预设里的
具名子代理、`send_message`、`list_agents`、`workflow`、`ralph`。这带来两个问题：

1. 想「今天不想要子代理」时没有开关——只能改装配文件；
2. 每加一个专职子代理（例如代码审查）都要写一份 agent preset 文件，改提示词要动 YAML。

本插件把上述工具全部收进来，做成**可勾选的 Agent 条目**：

```
聊天框「子代理」总开关 ─┬─ 关闭 → 模型完全不能使用子代理（含 DSH 原生工具）
                       └─ 打开 → 只放行被勾选的条目，并把「何时调用」写进系统提示
设置页「子代理」      ──── 条目表 / 权限 / 模型 / 闸门名单 / 模型自助管理
```

```powershell
#      dsh.profile.bundles: 追加 "dsh-ob-agent"
# 2) 安装（在 profile 目录）
cd C:\Users\17737\.dsh\profiles\web
pnpm install
# 3) 重启 DSH 进程，然后浏览器 Ctrl+F5（客户端 bundle 需要重新加载）
```

> 插件作者未声明免重启生效，因此安装/更新后必须重启 DSH。

### 2.1 改了插件代码，界面却没变化？

运行中的 DSH 用的是 profile 里**独立的一份副本**（`~/.dsh/profiles/web/node_modules/dsh-ob-agent`），
`npm run build` 只写仓库的 `lib/`。只构建不同步的话，症状与「代码没修好」一模一样：行为完全没变。
正确的更新顺序是：

```powershell
# 1) 仓库里构建（typecheck + 测试 + 三份产物）
cd C:\Users\17737\Code\other\DSH\plugins\dsh-OB-agent
npm run check
# 2) 让 profile 拿到新产物（二选一）
cd C:\Users\17737\.dsh\profiles\web
pnpm install                    # 重新链接 file: 依赖，推荐
# 或者只同步产物，速度更快：
# Copy-Item "<仓库>\lib\*" "C:\Users\17737\.dsh\profiles\web\node_modules\dsh-ob-agent\lib\" -Recurse -Force
# 3) 浏览器 Ctrl+F5；若界面仍无变化再重启 DSH 进程
```

判断是否同步成功：比较两边 `lib/client.js` 的哈希，或看 profile 副本的修改时间。

## 3. 界面

### 3.1 聊天框「子代理」面板（输入框上方）

面板结构与 DSH 官方的待办/队列面板一致：36px 首行 + 可展开列表，上圆角 12px、
0.5px 描边且无下边框，因此与下方输入卡片拼成一张连续表面。

| 元素 | 行为 |
| --- | --- |
| 首行图标 + **子代理** | 点击展开/收起条目列表（总开关关闭时不可展开）。 |
| 首行摘要 | 关闭时显示「已拦截全部 Agent 工具，模型无法调用子代理」；打开时显示已勾选数量。 |
| 首行右侧 **Switch** | 本会话总开关。打开时条目列表自动展开；关闭时保留勾选，再次打开即恢复。 |
| 条目行复选框 | 按「默认启用」规则预勾选，点行内任意处即切换并立即生效。 |
| 条目行右侧标签 | 模式（一次性 / 可继续对话）、只读权限标记、来源（DSH 原生 / 模型自建）。 |
| 条目名悬浮提示 | 该条目的「何时调用」提示词，方便核对模型看到的内容。 |
| **DSH 原生工具** 分组头 | DSH 自己实现的原生条目收在这一组里，**默认折叠**：平时只占一行，右侧显示该组已启用数量，点开才出现那 5 个复选框。 |

控件全部使用 DSH 自己的组件库（`@deepseek-ai/dsh-client-ui-primitives` 的
Switch / Button / Tag / Menu / Tooltip / DisclosureRow 与官方图标），配色、字号、
圆角、动效一律取设计令牌（`--dsw-alias-*` / `--dsw-font-*` / `--ds-*`），
因此自动跟随浅色/深色主题与「设置 → 外观 → 字号」偏好。

### 3.2 设置页「子代理」

- **全局**：新会话是否默认打开总开关、是否自动放行续话工具、可继续对话的子代理是否可
  回发消息给父代理、只读工具白名单、提示词可用变量、模型文档注入方式（path / inline / off）。

> **提示词可用变量**：只有列在这里的变量才允许出现在提示词中，且写法必须**严格**为
> `{{小写名字}}`（`{{ cwd }}`、`{{Cwd}}`、`{{cwd-x}}` 都会被拒绝）。原因是运行时的插值器
> 只认这一种写法，其余写法会抛错并打断**整个请求**。列表里的名字必须同时是当前会话装配里
> **真实注册过**的变量（本部署的各个预设都通过 `@deepseek-ai/dsh-persona` 注册了 `cwd` 与
> `model`）；某个预设没有注册而你仍引用它，请求同样会失败——不确定就把列表清空。

- **Agent 条目**：每条可编辑标识、名称、描述、两个提示词、运行模式（可多选）、后端
  （spawn / fork）、权限（完全 / 只读）、模型（下拉或手填，可选思考等级）、
  是否默认启用、是否纳管；支持上移/下移/复制/删除/新增。
- **自助管理**：是否允许模型创建/修改条目、可修改范围（仅自建 / 全部）、条目上限。
- **闸门（高级）**：逃生舱开关、按前缀拦截、按精确名拦截、豁免名单、打开总开关时的重挂名单。
  收起在官方的 DisclosureRow 里，平时不占版面。
- 底部有保存/恢复出厂；**校验不通过不会写入**（错误以中文列在顶部）。

整页栅格与 DSH 官方的「模型」设置页一致：720px 栏宽、0.5px 描边圆角卡片、胶囊按钮、
官方 Tag / Switch；模型选择用官方的两级菜单（provider → 模型）。

## 4. 语义说明（重要）

### 4.1 闸门怎么工作

每个 agent 作用域上装三层：

| 层 | 手段 | 作用 |
| --- | --- | --- |
| 隐藏层 | `tools.restrict({ deny })` | 让被拦截的名字从模型的工具清单里**消失**（只作用于继承面）。 |
| 执行层 | `tools.guard(...)` | 执行前拒绝，覆盖自有层重挂的工具；返回中文原因。 |
| 重挂层 | `agent.ctx.inject` + `apply` | 按勾选在 agent 自有层装配工具。 |

- **总开关关闭**：允许集合为空 → 隐藏层清掉继承面、守卫清掉一切残留 → 模型完全无法使用
  子代理与编排工具（包括它"记得"的工具名）。
- **总开关打开**：只有被勾选条目的工具名进入允许集合；其余照旧被拦截。
- **枚举继承面时查看者必须是 agent 本身**：拒绝名单由 `tools.schemas(agent)` 枚举出的名字
  算出。上游的 scope 参数是「查看者作用域键 = **agent 对象**」（`ctx.tools.get(name, agent)`，
  上游自己也这么调用）。历史版本误传 `agent.ctx`，得到空枚举 → 名单算空 → **隐藏层静默失效**：
  工具照旧出现在模型清单里，只有调用时才被守卫拒绝（典型症状是子代理看得见
  `list_agents` / `interrupt_agent` / `subagent*`，一调用就收到中文拒绝）。本仓库当前版本
  已修正；若你的部署仍是旧构建，按 2.1 把 `lib/` 同步到 profile 后重载插件。
- **混有不可隐藏名字时**：先尝试整批隐藏，再逐个处理；成功隐藏的名字保持隐藏，失败的名字
  仍由执行层守卫拒绝。相同名单和工具定义不会因自身发出的 `tools/change` 反复重装；工具
  重新注册或设置改变后会重新尝试。无法隐藏的名字会有一条 `dsh-ob-agent:` 中文告警。
- **可见不等于可执行**：`tools.schemas(agent)` 枚举的是完整可见面，包含继承工具与自有工具，
  不是「可被 restrict 的名字」清单。提供方直接在 agent 自有层注册的委派工具可能仍会显示，
  但执行层照旧拒绝。当前 DSH 的原生 `subagent` 就存在这一场景（见 4.7）；不能仅凭一个
  工具残留就判定整个隐藏层失效。
- **子代理**（`session.header.origin === 'subagent'`）只装前两层，不装配任何委派或编排
  工具 → 任何层级的子代理都不能再委派。唯一例外是「回发给直接父代理」的 `send_message`
  （见 4.5）：它是消息通道，不是委派能力。
- **`gate.enabled = false`**（逃生舱）：三层全部不生效，恢复 DSH 原生行为。

### 4.2 原生工具的三档实装

条目表里的「DSH 原生工具」条目按三档择一，取决于当前会话预设到底装配了什么：

| 档 | 条件 | 行为 |
| --- | --- | --- |
| A 放行 | 该名字已在当前作用域可见（预设已提供，如 `dsh-hy4` 下的 `workflow`） | 从拒绝集移除即可，不重复注册。 |
| B 重挂 | 预设没有提供（如 `code-review` 预设没有 delegation 组） | 由本插件在 agent 层调用对应实现包装配。 |
| C 不可用 | 实现包加载失败 / 缺 `workflowEngine` / 只读白名单交集为空 / provider 未注册 | 该条目本次不可用，日志给出中文原因；不影响其它条目。 |

### 4.3 会话选择存在哪里

会话级选择存放在插件配置 `sessions` 映射（键 = 会话 id）：

- 好处：不需要自定义 Remote / 投影 / HTTP 路由，界面与主机读同一份快照；
- 代价：它是**配置文件里的会话状态**，会按最近使用裁剪（上限 120 条会话）；
- 新会话没有记录时回落到「总开关默认值 + 默认启用条目」。

### 4.4 模型自助管理

开启后模型可用 `agent_create` / `agent_update` / `agent_list`：

- 默认作用域 `own`：模型**只能创建/修改自己创建的条目**，内置与用户条目只读；
- 每次都过同一套校验（标识、长度、提示词变量、只读白名单），失败返回中文原因且不写入；
- 每次创建/修改留一条审计日志（`dsh-ob-agent 审计：…`）；
- **新工具下一轮请求才可见**，`agent_create` 的结果文案会明确告知模型；
- 写入的提示词会成为系统提示与子代理 persona，风险与用户手建等价 —— 因此该能力由
  「总开关 + 「Agent 自助管理」条目勾选」双重授权，可随时关闭。

### 4.5 子代理回发给父代理

上游 `send_message` 是**双向**的：既能从父代理发给直接可继续对话的子代理，也能从
**驻留的可继续对话子代理**发回它的直接父代理。但子代理作用域本来整片受闸门管辖，
于是子代理只有最终回复这一条出口——中途发现方向错了、缺少输入、需要追加信息都传不出来。

设置页的「子代理可回发消息给父代理」（默认**开启**）打开后：

| 项 | 行为 |
| --- | --- |
| 放行范围 | 子代理内部**只**放行 `send_message` 一个工具，目标是它的直接父代理；`interrupt_agent`、`list_agents`、`workflow`、`ralph` 与全部委派工具照旧被拦。 |
| 生效对象 | 只有**可继续对话**的子代理。模式由子会话日志里的 `subagent/descriptor` 判定；判定不出来（读不到该事件）时按放行处理——判定失败不该变成「子代理失去唯一回发通道」。 |
| 一次性子代理 | 不放行。它调用回发必然被上游按相邻关系拒绝，给一个永远失败的工具只会白耗一轮。 |
| 装配方式 | 在本插件里由 `send_message` 的原生实现**只重挂这一个工具**到子代理自有层；即使父会话那一侧是「档 A 放行」（工具来自预设），子代理也能拿到，两种来源表现一致。 |
| 提示词 | 子代理作用域**不再**照抄主会话的能力清单（那会让它以为自己能委派），改为只渲染一行回发说明与父代理会话 id。 |
| 授权 | 相邻关系与「你是否是驻留的可继续对话子代理」由 `ctx.subagents.sendMessage()` 在服务层校验，本插件只负责不拦。 |

关闭该开关后子代理回到「只能把结论写在最终回复里」的行为。`gate.enabled = false`
（逃生舱）时本插件完全不干预，`send_message` 按 DSH 原生行为可用。

### 4.6 能力清单只列**真的装上了**的条目

系统提示段里的「本会话已启用以下 Agent 能力」与 `list_agents` 结果开头的能力清单，回答的是
「你现在能用哪些子代理工具」。因此它们必须反映**装配结果**，而不是条目里的**声明值**：

- 条目里的 `toolNames` 是声明（尤其 `subagent_native` 的 `subagent_hy4` —— 它来自某个具体
  预设，换一个预设就根本不存在）；
- 协调器每轮都会算出「哪些条目真的装上了」（档 A 放行 / 档 B 重挂成功 / 档 C 落空、
  实现包加载失败、装配抛错），这份结论现在会被清单读取，落空的条目直接不出现。

**判定的两个方向都要保守**：只要条目有任意一个安装键可用就算可用（双模式子代理只有一个
模式装上时，仍要如实宣传它能用）；拿不到判定信息时（`ALWAYS_AVAILABLE`）一律按可用处理 ——
「模型以为有、调用才发现没有」只浪费一轮，而「实际有、清单里不写」会让它根本不去用。

> 这一条是实测发现并修掉的：在没提供 `subagent_hy4` 的预设下勾选「DSH 原生具名子代理」，
> `list_agents` 会列出它、调用却得到 `unknown tool`。协调器当时**已经**判出档 C 并写了
> 中文告警，只是渲染层没读这个结论。

### 4.7 原生 `subagent` 残留：已定性的上游自有层边界

DSH `0.1.7-rc.2` 的 Web 预设为原生 `subagent` 开启了 `modelSelectionSettings: true`。
`@deepseek-ai/dsh-tool-subagent` 在这种配置下会监听 `agent/created`，通过每个 agent 的
`ctx.inject(...)` 注册工具，**子代理也包含在内**。于是原生 `subagent` 属于子代理自有层，
不是隐藏层能够限制的继承工具。未开启该设置的 `subagent_fork` 仍是预设的继承贡献，能被隐藏。

上游规则明确：restriction 只过滤全局层与祖先层，**永不遮掉本作用域自有层注册**。
`restrict()` 校验名单时，只要其中一个名字不在继承面就整批失败，错误里称它为
`unknown global tool` —— 这不等于它没有注册，而是它不属于可限制的继承名字。

证据需要区分来源：

- **历史模型请求实测**：可继续对话的子会话 `3509baff-3007-4fa6-ba01-5ee402654831` 的
  `request/header` 记录了 48 个工具；`subagent` 和 `send_message` 可见，`workflow`、
  `subagent_fork`、代码审查委派工具、`list_agents` 与 `interrupt_agent` 已隐藏。另一个子会话
  的真实调用证实 `subagent` 被执行层拒绝，回发消息也已实测成功。
- **同版本真实登记表的隔离复现**：在真实 Cordis / ToolRuntime 上，让预设提供继承工具、
  提供方在子代理自有层注册 `subagent`，运行当前协调器，得到下面的告警。它是隔离复现输出，
  **不是声称已从历史宿主终端取回的那一行**；`own-layer-probe` 是复现 agent 的标识。

```text
dsh-ob-agent: agent own-layer-probe 有 1 个名字无法进入隐藏层（它们仍会被执行层守卫拒绝）：subagent（tools.restrict() names unknown global tool "subagent"; known global tools: interrupt_agent, job_list, list_agents, read, send_message, subagent_code_review, subagent_fork, workflow）
```

隔离复现还验证了：其它继承名字被隐藏；`send_message` 原生实现重挂成功；`subagent` 调用
被守卫拒绝、普通工具 `job_list` 放行；稳定状态下连续重算 20 次，新增 `tools/change` 为 0，
隐藏失败告警只出现一次。仓库装配测试覆盖该边界，以及「继承面与自有层恰好同名」的情况
（此时 restrict 可能成功且无告警，但自有版本仍可见）。

**处理结论**：当前保留执行层守卫和已收敛的隐藏层，不为这个不可限制的名字再次改动协调器。
如果要求 `subagent` 从子代理模型清单里也彻底消失，需要在提供方取消子代理的自有层注册，
例如上游模型选择装配跳过子代理、或有针对性地调整预设装配。仅反复调用 restrict 无效。
直接关闭 `modelSelectionSettings` 虽能改变注册位置，却同时影响主会话原生子代理的模型选择，
不能作为无副作用的修复；也不应全局禁用原生工具、篡改工具登记表私有层、或修改请求快照伪装隐藏成功。

## 6. 内置「代码审查」条目的行为

沿用原「代码审计（Hy4）」的模型 `opencode-go / hy4-preview`、一次性模式和完全权限，
但**触发时机恢复为文件改动即审查，同时以成本为硬约束**：

1. 用户明确要求审查时立即调用；否则主模型每次实际修改文件后都立即调用 `subagent_code_review`，
   包括代码、配置和文档。一次工具调用同时修改多个文件时只审查一次；后续独立的文件修改仍需再次触发，
   不要推迟到整个任务结束。纯问答和只读探索不调用。
2. 审查返回后先独立核实：有证据且值得修复的风险再修；误报、低风险或修改成本高于收益的建议可说明理由不采纳。
   审查建议不是命令，不要无脑全部照做。
3. 首次审查后，不要因为落实该次建议就自动复审；特别是只改提示文案、注释、格式、测试断言或其它
   无行为变化内容时，禁止再次调用。只有后续修复引入新的、现有测试无法覆盖的安全、数据或兼容性高风险行为，
   才允许针对新风险额外聚焦审查一次；新的独立文件改动仍按原规则触发，同一问题最多复审一次，禁止形成修改—审查循环。
4. 审查员只看变更和必要上下文，不做无关全仓扫描或重复测试；优先使用已有检查结果，仅在验证具体高风险问题
   确有必要时执行最小命令。只报告值得修复的具体风险，给出位置/证据、触发条件、影响、最小修复方向和严重级别；
   不为凑数提出风格、措辞或无证据的建议，疑点需标明待验证。

> **依赖提示**：这一条沿用原「代码审计（Hy4）」的模型路由 `opencode-go / hy4-preview`。
> 若你的 `~/.dsh/settings.yaml` 里没有配 `opencode-go` 这条路由，勾选后 `subagent_code_review`
> 会在启动时失败——届时在设置页把该条目的「模型」清空（继承主会话）或改成你已配置的路由即可。

> 想让它回到「读 `review/GUIDE.md`、按声明的范围跑编译/接口/浏览器测试、产出
> `review/reports/REVIEW-*.md` 报告、更新 `.last-review.json`」的重型流程版，把设置页里
> 的身份提示词换成 `~/.dsh/.agent-presets/code-review/agent.cordis.yml` 里的 persona 即可
> （该文件同时备份在 `plugins/dsh-review-presets`）。

## 7. 验收清单（安装后逐条核对）

1. 设置页出现「子代理」，8 条内置条目可编辑（3 条插件角色 + 5 条 DSH 原生工具）；
   若你的设置段来自旧版本，启动日志里应有一行「出厂默认已迁移到第 4 版」。
2. 新会话默认**关闭**总开关；关闭时继承面里的 `subagent*` / `send_message` /
   `interrupt_agent` / `list_agents` / `workflow` / `ralph` / `agent_*` 应被隐藏；提供方自有层
   的同类工具可能仍可见（见 4.7），但所有命中闸门且未放行的名字均不能执行，调用应被拒绝。
3. 打开总开关 → 复选框按「默认启用」勾选；用请求提示检查器确认系统提示里出现
   「本会话已启用以下 Agent 能力」一段，且内容与勾选一致。
4. 勾选「代码审查」→ 出现 `subagent_code_review`；让模型修改代码或文档，
   观察每次文件修改后立即触发一次审查；同一工具调用改多个文件时只调用一次。仅按审查建议改提示文案时不应二次调用。
5. 取消勾选 → 该段与工具消失，其它已勾选项不受影响。
6. 同一条助手回复里并行发起两个不同子代理调用 → 均成功。
7. 勾选 `general`（可继续对话）→ 返回持久 id，`send_message` 可续话（续话工具自动放行）。
8. 权限切「只读」→ 子代理没有 `pwsh` / `bash` 等命令工具。
9. 模型自助：让主模型 `agent_create` 建一个条目 → 返回工具名与「下一轮可用」；下一轮能
   调用；设置页出现「模型自建」条目；日志有审计行。
10. `agent_update` 改内置条目被拒；`agent_list` 能列出未勾选条目。
11. 在 `code-review` 会话预设下打开总开关，展开面板里的「DSH 原生工具」分组并勾选
    `workflow` → 档 B 重挂成功可用（若该预设未装配工作流引擎，则显示为不可用并有中文日志）。
12. 面板里「DSH 原生工具」分组默认是**折叠**的：平时只占一行，点开才出现 5 个复选框。
13. 刷新页面 / 换会话 → 各会话选择互不影响；把设置页的「启用闸门」关掉 → 立即恢复
    DSH 原生行为。
14. 子代理回发（默认开启）：让主模型委派一个**可继续对话**的子代理（如 `general`），
    在委派说明里要求它「先回一条进度消息再给结论」→ 子代理的 `send_message` 应当成功
    （`agent_id` 填主会话 id），主代理随后收到这条消息；同一子代理调用 `list_agents` /
    `interrupt_agent` / 委派工具仍应被拒。把设置页的「子代理可回发消息给父代理」关掉并保存，
    再让子代理回发 → 应当收到中文拒绝。
15. 子代理工具清单与执行权限**分开验收**：可继续对话的子代理应有 `send_message`；
    继承面提供的 `list_agents` / `interrupt_agent` / 委派与编排工具应被隐藏。当前 Web
    预设可能仍显示自有层原生 `subagent`（见 4.7），必须确认它不能执行，不要误报整层失效。
    若多个继承工具也残留，才按 2.1 核对 profile 副本并检查 4.1 的查看者作用域与隐藏告警。
16. 能力清单**只列真的装上了的条目**（见 4.6）：勾选「DSH 原生具名子代理」后，`list_agents`
    与系统提示段里出现的名字，逐个调用都应当有正常响应；当前预设没提供的名字**不应出现**
    （同时 DSH 日志里应有一条 `dsh-ob-agent: 条目 subagent_native 本会话不可用：当前会话预设
    没有装配这些具名子代理工具：…`）。若清单里出现了调用即 `unknown tool` 的名字，说明
    profile 副本还是旧构建，按 2.1 同步后重启。

| 模型说工具被拒绝 | 主会话检查总开关或条目是否勾选；子代理除回发外禁止 Agent 能力，守卫的中文拒绝信息会说明。 |
| 子代理只残留原生 `subagent`，其它委派/编排已隐藏 | 检查提供方是否开启 `modelSelectionSettings` 并在 agent 自有层注册它；这是已定性的继承限制边界，不是执行层漏拦。按 4.7 核实工具请求清单、拒绝结果与告警；不要靠反复重装隐藏层处理。 |
| DSH 持续占满一个 CPU 核心 | 检查终端里的 `dsh-ob-agent:` 隐藏层告警，并确认 profile 安装副本含有本次重算收敛修复；若需立即恢复服务，在 profile 补丁的 `id: dsh-ob-agent` 下设置 `disabled: true`，重启 DSH。 |
| 子代理里 `send_message` 被拒 | 三种可能：① 它是**一次性**子代理（只有可继续对话的子代理能回发给父代理）；② 设置页关了「子代理可回发消息给父代理」；③ 目标填的不是它的直接父代理。日志里若有 `未能装配 send_message` 则是原生实现包没加载出来。 |
| `workflow` 显示不可用 | 该会话预设没有装配 `@deepseek-ai/dsh-workflow`（缺 `workflowEngine` 服务）。 |
| 想临时回到原生行为 | 设置页 → 闸门 → 关闭「启用闸门」。 |

## 9. 已知限制

- 会话选择存在设置文件的 `sessions` 映射里（按最近使用裁剪到 120 条），删除会话不会自动
  清理对应记录。
- 子代理「可继续对话 / 一次性」的判定读的是子会话日志里的 `subagent/descriptor`（先读
  `subagent` 投影，读不到再扫子会话自有事件）。上游若改掉这条事件或移除同步事件读取，
  判定会退化为「未知」并按**放行**处理——此时一次性子代理也会看到 `send_message`，
  调用会被上游的相邻关系校验拒绝，属于多余的一次失败调用，不会越权。
- 子代理回发只放开「回发给直接父代理」这一个方向。子代理之间的横向通信、子代理主动
  唤起兄弟代理都不支持（上游也没有这个能力）。
- 隐藏层依赖 `tools.schemas(agent)` 枚举名字（作用域语义见 4.1）。PTC（`run_code`）呈现模式
  下枚举结果会额外包含传输工具 `run_code` 本身 —— 它不在闸门名单里，因此不影响拒绝名单；
  被收敛到传输层之后的同名调用仍由执行层守卫兜住。
- 只读权限通过工具白名单实现；白名单与真实可见工具的实际交集为空时条目停用（不降级）。
  另外，把上游的传输工具名（`run_code`）写进只读白名单会让子代理创建失败 —— 它属于
  「可见但不可 restrict」的保留名，默认白名单（`read`/`read_image`/`glob`/`grep`）不受影响。
- **子代理自有层**里命中闸门且未放行的工具，`tools.restrict` 无法隐藏：该名字
  仍留在模型清单，但调用时由执行层守卫拒绝；其它能隐藏的继承面名字不受影响。
  当前原生 `subagent` 的提供方注册路径与实测见 4.7。只在继承面不存在同名工具时会触发
  `unknown global tool` 告警；若存在同名继承工具，限制可能成功而自有版本仍可见，因此
  「无告警」不保证无残留。需要完全消失时应取消提供方的自有层注册。
- 预设切到中途新出现的同名原生工具，若本插件已重挂过它，仍以本插件的实例为准
  （两者来自同一实现包，行为等价）。
- 模型自助管理只能受限于设置里的上限与作用域，不能限制它写什么提示词内容 —— 审计日志与
  「模型自建」标记是主要的事后控制手段。
- 客户端 bundle 在顶层 `require` DSH 的 UI 组件库（`@deepseek-ai/dsh-client-ui-primitives`）。
  该共享模块目前由 shell 提供，运行期不做「模块是否整体存在」的兜底；能做的是两层保护：
  `src/client/host-ui.tsx` 解析单个图标时缺失就退化为空占位（一个图标没了不会带走整块界面），
  `apply` 入口自检结构组件并打印中文原因 —— **只告警，不跳过注册**（跳过注册会让整个界面
  消失，是更糟的失败模式）。若某个 DSH 版本/裁剪版整体不再提供该模块，按控制台提示对齐版本。
